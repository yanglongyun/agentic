# 从零开始打造一个 Agent：用 JavaScript 跑通模型、工具和上下文

我想做一个这样的工具：

打开浏览器，输入“看看这个项目，找出问题并修改”，它就能读取文件、执行命令、修改代码，再把结果告诉我。

我希望它能部署在自己的服务器上。界面能看到执行过程，关掉页面后还能找到聊天记录，对话变长也能继续进行。

于是，我做了一个叫 **agentic** 的项目。后端使用 JavaScript 和 Node.js，前端使用 React，数据保存在 SQLite 中。

这篇文章就沿着这个项目，讲讲一个 Agent 是怎样从模型请求，一步步长成可用程序的。

## 一、先跑通一次模型请求

第一步，我先把模型调用单独放进 `server/ai/`。

它接收几样东西：指令、消息、模型名称、配置，以及可以调用的工具。

其中，指令告诉模型这次应该怎样工作；消息提供用户的问题和之前发生的事情；工具定义告诉模型，程序能替它执行哪些操作。

这一层负责发送 HTTP 请求、解析模型响应、处理流式输出和请求重试。

至于聊天记录保存在哪里、页面怎样显示，都留给其他部分处理。

这样，后面调试时就容易定位：请求失败，先看 AI 模块；工具没执行，去看 Agent；消息没保存，检查 API。

## 二、让模型通过工具操作环境

假设用户提出一个任务：

> 看一下当前目录，找到配置文件，把服务端口改成 3000。

要完成它，程序需要经历几个步骤：查看目录、读取配置、修改文件，必要时再执行验证命令。

我先提供四个工具：

- `shell`：执行命令。
- `read`：读取文本或图片。
- `write`：写入文件。
- `edit`：精确替换文件内容。

每个工具都有两部分：**给模型看的定义，以及程序实际执行的方法。**

工具定义放在 `tools.js`，就是一个普通数组，写清楚名称、用途和参数。执行代码放在 `functions/`，一个工具一个文件。

模型需要读文件时，会返回一个工具调用，其中包含工具名称、参数和 `call_id`。程序根据名称找到对应函数，执行后把结果带着同一个 `call_id` 交回去。

这个 ID 用来说明：这份结果，对应的是哪一次调用。

模型只提出调用要求，真正执行命令、读写文件的是服务器进程。工具能够做什么，也取决于这个进程拥有的权限。

## 三、Agent 的核心，是把结果送回模型的循环

有了模型调用和工具执行，就可以把它们连接起来：

```text
用户提出任务
    ↓
把上下文发给模型
    ↓
模型返回内容，以及可能的工具调用
    ↓
有工具调用 → 执行工具 → 把结果加入上下文 → 再次请求模型
    ↓
没有工具调用 → 本轮结束
```

下面用一段简化代码展示主干流程。实际项目还包含流式事件、压缩、图片和取消处理。

```js
async function runAgent(instructions, messages, model, config) {
  while (true) {
    const response = await callModel(instructions, messages, model, config, tools);

    messages.push(...response.output);

    const calls = response.output.filter((item) => item.type === "function_call");

    if (calls.length === 0) {
      return response;
    }

    for (const call of calls) {
      const result = await runTool(call, config);

      messages.push({
        type: "function_call_output",
        call_id: call.call_id,
        output: JSON.stringify({
          success: !result.failed,
          text: result.text,
        }),
      });
    }
  }
}
```

关键就在 `messages.push()`：**工具结果会成为下一次模型请求的上下文。**

读取文件后，模型才能根据真实内容决定下一步；命令执行失败后，它也能看到错误，再决定是否调整。

我的项目里，`agent/index.js` 负责这个循环。`runner.js` 只接收一次工具调用，执行对应函数，返回结果。

循环没有固定轮数上限。运行仍受超时和取消信号控制，用户可以点击停止。

## 四、目录按照请求经过的顺序组织

把主干跑通后，我把代码集中在两个主要目录里：

```text
ui/                      浏览器界面
  src/
  dist/                  构建产物

server/
  index.js               启动服务、初始化数据库、托管 ui/dist
  db.js                  数据库表结构
  api/                   接口与业务处理
  ai/                    模型请求
  agent/
    index.js             Agent 循环
    tools.js             工具定义数组
    runner.js            工具分发与执行
    compact.js           上下文压缩
    functions/
      shell.js
      read.js
      write.js
      edit.js
```

API 按 URL 一层层分发。比如发送消息：

```text
WS /api/chat → send

server → api → sessions → [id] → messages → post.js
```

每层用 `index.js` 处理分发，最终进入对应 HTTP 方法的文件。

当前项目的 SQL 直接写在接口文件里，建表语句统一放在 `db.js`。接口负责取数据、调用 Agent、保存结果；Agent 通过事件向外报告进展。

这样的结构方便我顺着一次请求，从入口读到具体实现。

## 五、聊天记录要保留模型真正返回的结构

做到这里，会遇到一个问题：下一次用户发消息时，应该把什么交给模型？

如果只保存聊天气泡里的文字，就会丢掉工具调用、调用参数、工具结果，以及模型返回的 reasoning 等内容。

所以，我的项目采用 Responses 格式保存消息。

用户输入构造成标准的 user message；模型完整有效返回后，把 `response.output` 中当前支持的 `message`、`reasoning`、`function_call` 逐项保留。工具执行结果则构造成 `function_call_output`。

**展示用的文字和下一轮请求需要的上下文，是两种不同用途的数据。**

流式生成时收到的文字增量，用来让页面及时显示。等模型完整返回，再使用完整 output 对象保存消息，不拿增量重新拼造模型对象。

数据库先用三张表：

- `sessions`：会话 ID、标题和时间。
- `messages`：所属会话、消息块 `item`、实际用量 `usage` 和时间。
- `compactions`：压缩摘要，以及摘要覆盖到的消息位置。

其中，`item` 保存消息对象的 JSON，`usage` 保存模型实际返回的用量。

业务接口从数据库取出上下文后，再交给 Agent。工具循环期间，Agent 继续使用这一个消息数组追加内容。

## 六、流式显示之后，还要确认哪些内容真正保存了

我的后端通过 WebSocket 向浏览器持续发送业务事件。网页订阅会话后，可以陆续收到文字、工具结果、保存确认和运行状态；断线后重新订阅恢复状态。

Agent 对外输出九种事件：

```text
message               正文
reasoning             思考内容
function_call         工具调用
function_call_output  工具结果
retry                 即将重试
usage                 本次模型请求的实际用量
compact               压缩开始或完成
done                  整轮结束
error                 终止性错误
```

这里有个很容易忽略的区别：**页面已经显示出来，不代表数据库已经保存成功。**

例如，模型要求执行两个工具。第一个完成了，第二个执行到一半，用户点击停止。这时需要明确：哪些内容保留，哪些内容还只是临时状态。

我采用的规则是：用户输入先保存；一次模型响应和对应的工具结果，等这一组全部完成后一起提交。

数据库提交成功，API 才通过独立的 messages.saved 业务事件交付保存确认，告诉前端每条消息的真实 ID。前端据此更新本地记录。

失败或取消时，丢弃当前尚未提交的那一组，保留之前已经保存的内容。

需要注意，数据库事务只能管理记录。已经执行的命令、已经修改的文件，不会随着消息回滚自动恢复。

有了保存确认，回复结束后就不必再查询一次全部消息和会话列表。侧栏信息、压缩记录，也可以随事件直接更新。

## 七、对话变长后，用摘要接续上下文

持续把历史消息追加进去，上下文就会越来越长。

我把压缩做成一个单独模块，放在 `compact.js`，在每次请求主模型前检查是否需要执行。

判断依据是：

```text
上一次模型响应的 usage.total_tokens >= 配置的 compact_at
```

新一轮用户输入时，业务接口从数据库读取最近一次模型输出的 usage；工具执行后继续循环时，使用刚刚收到的 usage。

这里不累加历史请求的用量，也不根据文字长度估算。

不过，这个数反映的是上一次请求的实际用量，并不包含之后新增的用户输入和工具结果。因此，它是当前项目的压缩触发依据，不能保证下一次请求一定不会超过窗口。阈值需要留出余量。

达到阈值后，压缩模块会保留最近的一部分消息，为较早的内容生成摘要。选择截断位置时，还要保证工具调用和对应结果完整配对。

摘要生成后，先写入 `compactions`，保存成功再继续主模型请求。

下一次打开这段会话时，上下文这样组装：

```text
最新摘要 + 摘要覆盖位置之后的消息
```

压缩表中的 `through_id`，记录“已经总结到哪条消息”。原始历史仍然保留，用户还能翻看。

摘要会舍弃细节，所以保留最近消息、正确选择边界，以及写清摘要要求，都很重要。

## 八、图片也沿用同一套消息流程

最近，我给输入框增加了图片功能：可以选择、粘贴、预览和移除图片，每条消息最多五张，也可以只发图片。

图片进入模型时，使用标准的 `input_image`，前提是配置的模型支持图片输入。

存储时，我选择把图片写入文件，数据库只记录图片地址。等真正请求模型时，再读取文件，转成此次请求需要的 Data URL。

流程是：

```text
用户选图 → 保存文件 → 消息记录图片地址
                         ↓
                   请求模型前读取文件
                         ↓
                   构造 input_image
```

这样，Base64 不会反复出现在数据库和消息事件里。从历史记录恢复上下文时，也沿用同样的处理过程。

工具读取图片后的结果同样可以包含图片，不需要额外伪造一条用户消息。

## 最后，让它成为一个能安装、能使用的程序

核心循环之外，还需要登录、配置、历史记录、取消执行，以及安装和启动入口。

我的前端构建到 `ui/dist`，由同一个 Node.js 服务托管。发布包把运行所需的 Node.js 和程序一起打包，安装脚本负责部署；对应版本发布后，用户可以通过一行命令安装。

这些部分决定了一个项目能否从开发目录走到自己的服务器上。

回头看，最值得先理解的，是这条完整路径：

**用户输入 → 组装上下文 → 请求模型 → 执行工具 → 回传结果 → 继续循环 → 保存并显示。**

想动手做的话，可以先完成一个更小的版本：只接一个模型，只提供一个 read 工具，跑通“读取文件，再根据文件回答”的过程。

然后再加入写文件、执行命令、消息保存、流式界面和上下文压缩。

每多加一步，都让自己能回答三个问题：这一步输入什么，输出什么，失败后留下什么。

当这条链路足够清楚，Agent 就成为了一段可以阅读、调试和持续改进的程序。
